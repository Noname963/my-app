저는 공장 설비의 상태 데이터를 관찰하고, 이상 징후를 근거로 원인을 좁혀 정비 의사결정에 도움이 되는 고장진단 전문가를 목표로 하고 있습니다. 이 포트폴리오는 “전문가라고 주장하는 페이지”가 아니라, 진단 문제를 어떻게 정의하고 검증해 나갈지를 보여주는 증거 중심의 기록입니다.

01 · POSITIONING

제가 되고 싶은 사람

생산 현장의 고장은 단순히 “기계가 멈춘 사건”이 아니라 품질, 납기, 안전, 비용에 영향을 주는 문제입니다. 저는 센서와 운전 데이터를 통해 이상을 조기에 발견하고, 가능한 원인을 체계적으로 좁혀 현장이 더 빠르고 근거 있게 대응하도록 돕는 진단 전문가로 성장하고자 합니다.

01

이상 징후를 읽는 눈

진동·온도·전류·소음 등 상태 정보에서 정상과 다른 패턴을 찾고, “무엇이 달라졌는가”를 먼저 설명하는 역량을 기릅니다.

02

원인을 좁히는 사고

하나의 수치만 보고 결론 내리기보다 설비 구조, 운전 조건, 고장 모드를 함께 보고 여러 가설을 비교하는 습관을 만듭니다.

03

현장이 쓰는 결과

진단의 끝은 그래프가 아니라 정비 판단입니다. 결과를 “어디를, 왜, 언제 확인해야 하는가”까지 연결하는 것을 목표로 합니다.

현재 상태: 아직 실제 경력과 성과 수치는 입력되지 않았습니다. 아래 항목은 지원을 위해 만들 진단 프로젝트 계획이며, 실제 수행 후 데이터·수치·링크로 교체하는 것을 전제로 구성했습니다.

02 · DIAGNOSTIC WORKFLOW

저의 고장진단 사고 순서

설비를 보자마자 고장명을 맞히는 것보다, 재현 가능한 순서로 원인을 좁히는 능력을 증명하겠습니다.

현상 정의언제, 어떤 조건에서, 무엇이 평소와 달라졌는지 기록
데이터 수집진동·온도·전류·RPM·부하 등 비교 가능한 정보 확보
특징 추출추세, RMS, 피크, 주파수 성분 등 이상을 설명할 특징 확인
원인 가설불평형·정렬 불량·베어링·캐비테이션 등 후보를 설비 구조와 연결
검증·제안추가 점검으로 가설을 확인하고 정비 우선순위와 다음 행동 제안

학습 및 증명 예정 기술

실제로 프로젝트에서 사용한 항목만 남기고, 사용하지 않은 기술은 삭제할 예정입니다.

진동 분석 기초 FFT / 주파수 분석 RMS / Peak / Kurtosis 트렌드 분석 온도 / 전류 상태감시 Python 데이터 분석 이상 탐지 기초 설비 FMEA 관점

프로젝트에서 반드시 남길 증거

“분석할 줄 압니다”라는 문장보다 직접 확인 가능한 자료를 남기는 것을 원칙으로 합니다.

원본/샘플 데이터 분석 노트북 또는 코드 그래프와 해석 문제·과정·해결·결과 README 커밋 이력

03 · PROJECTS

고장진단 포트폴리오 프로젝트

아래는 지원 직무와 직접 연결되도록 설계한 프로젝트입니다. 아직 수행 전이므로 성과를 지어내지 않고 “보강 예정”으로 표시했습니다.

Project 01 · 모터 베어링 이상 진단

진동 데이터에서 정상/이상 차이를 찾고, 주파수 성분을 근거로 고장 후보를 설명하는 프로젝트

설계 단계
문제

어떤 불편인가

모터는 고장 전까지 겉으로 정상처럼 보일 수 있습니다. 베어링 상태 악화를 조기에 구분할 수 있는 데이터 기준이 필요합니다.

과정

무엇을 결정하고 왜

정상/이상 데이터의 시간 파형과 스펙트럼을 함께 비교하고, 운전 조건 차이가 결과에 미치는 영향을 분리해서 보겠습니다.

해결

무엇을 만들 것인가

Python 기반 분석 노트북, 특징값 비교표, 주파수 스펙트럼 시각화, 진단 근거 요약 문서를 만들 계획입니다.

결과

무엇이 달라졌나

(보강 예정) 실제 데이터 분석 후 분류 정확도, 구분 가능한 특징, 한계와 오진 가능성을 수치로 기록합니다.

Project 02 · 펌프 캐비테이션 징후 탐지

운전 조건과 상태 신호 변화를 함께 보고 캐비테이션 가능성을 조기에 판단하는 프로젝트

설계 단계
문제

어떤 불편인가

펌프 이상 소음이나 진동이 커진 뒤 대응하면 성능 저하와 부품 손상으로 이어질 수 있습니다. 초기 징후를 객관적으로 설명할 기준이 필요합니다.

과정

무엇을 결정하고 왜

유량·압력·진동 등 운전 정보를 함께 보며 단순 진동 증가와 운전 조건 변화가 섞이지 않도록 비교 기준을 정의합니다.

해결

무엇을 만들 것인가

조건별 데이터 비교 대시보드 또는 분석 리포트와 “추가 확인이 필요한 조건”을 정리한 진단 체크리스트를 만들 계획입니다.

결과

무엇이 달라졌나

(보강 예정) 실제 수행 후 탐지 기준, 오탐 사례, 현장 적용 시 필요한 추가 센서/점검 항목을 기록합니다.

Project 03 · 컨베이어 구동부 상태 모니터링

모터·감속기·베어링의 상태 변화를 추세로 관리해 점검 우선순위를 정하는 프로젝트

설계 단계
문제

어떤 불편인가

컨베이어는 생산 흐름과 직접 연결되므로 갑작스러운 정지는 라인 전체에 영향을 줄 수 있습니다. 정기점검만으로는 변화 시점을 놓칠 수 있습니다.

과정

무엇을 결정하고 왜

절대값 한 번보다 시간에 따른 변화율을 우선 보고, 부하·속도와 함께 비교해 “정상 변동”과 “이상 추세”를 구분합니다.

해결

무엇을 만들 것인가

설비별 상태지표 추세표, 경고 기준 초안, 이상 시 점검 순서를 연결한 간단한 상태 모니터링 프로토타입을 만들 계획입니다.

결과

무엇이 달라졌나

(보강 예정) 수행 후 어떤 지표가 조기 경고에 유효했는지, 점검 우선순위 결정에 얼마나 도움이 되는지 정리합니다.

04 · RECORD

전문성은 결과와 기록으로 쌓겠습니다

진단 프로젝트 하나가 끝날 때마다 “프로젝트 카드 하나”만 늘리는 것이 아니라, 무엇을 시도했고 왜 바꿨는지 Git 커밋과 문서로 남기겠습니다.

1. 데이터와 문제 정의

설비, 고장 모드, 데이터 출처, 분석 목표, 평가 기준을 README에 먼저 작성합니다.

2. 분석 과정 기록

가설 변경, 실패한 접근, 특징 선택 이유를 작은 단위의 커밋 메시지와 노트로 남깁니다.

3. 결과를 숫자와 그림으로

가능하면 정확도, 오탐/미탐, 시간 단축, 탐지 시점 등 실제 측정 가능한 수치로 정리합니다.

4. 현장 적용 한계까지 적기

데이터 부족, 운전조건 변화, 센서 위치 등 진단을 어렵게 만든 조건과 다음 실험 계획을 함께 씁니다.

커밋 메시지 예시
“베어링 데이터 정상/이상 구간 분리” → “FFT 비교 추가” → “부하 조건별 오탐 원인 정리” → “진단 리포트 v1 작성”
